# Tureed — أساس المشروع (Foundation)

سوق مصري عام (منتجات + عقارات + خدمات) بلوحة تحكم كاملة، متعدد اللغة (عربي/إنجليزي)،
وقابل للتوسع في الأقسام والمناطق من غير ما حد يلمس الكود.

## صفحة البائع بقت زي صفحة فيسبوك + تسجيل دخول أول مرة بيجمع بيانات أكتر

- **أول تسجيل دخول (OTP) بيوديك لصفحة `/onboarding`**: صورة غلاف، صورة شخصية، الاسم، واتساب، الموقع، تصنيف المتجر (اختياري "لو محتاج")، نبذة — كل حاجة اختيارية غير الاسم، وتقدر تدوس "تخطي دلوقتي". الدخول تاني (بعد أول مرة) لسه رقم موبايل وكود بس، من غير فورم
- **صفحة `/seller/[id]` بقت فعليًا زي صفحة فيسبوك**: صورة غلاف كبيرة، الصورة الشخصية فوقها متداخلة، الاسم، Badge التوثيق، التقييم، تصنيف المتجر، الموقع، نبذة، وكل الإعلانات المنشورة — **أي حد** (مشتري أو زائر مش مسجل) يقدر يفتحها ويشوفها، وفيها زرار **"شارك"** يقدر يستخدمه صاحب المتجر أو أي زائر يبعت لينك الصفحة
- **الإعدادات اتشالت من قدام عينك**: مش هتلاقيها ظاهرة في صفحة `/profile` تاني — دلوقتي `/profile` بقت واجهة إدارة بسيطة (ملخص صغير + كل إعلاناتك تتحكم فيها)، وفيها زرار **"⚙️ تعديل الإعدادات"** بيوديك لصفحة منفصلة `/profile/settings` فيها كل الحقول دي (بما فيها رقم الموبايل بيتعرض بس مش قابل للتعديل، لأنه هو نفسه حساب تسجيل الدخول)
- **زرار "تعديل الإعدادات" ده بيظهر بس لصاحب الصفحة نفسه** لما يفتح صفحته — زي بالظبط لما تفتح صفحة فيسبوك بتاعتك وتلاقي "Edit Profile" ظاهر، لكن أي حد تاني بيفتحها شايف المحتوى بس من غير أي زرار تعديل
- **لوحة التحكم**: صفحة "المستخدمين" اتحولت لتبويب "المستخدمين والملفات" — بتعرض صورة كل حساب واسم متجره، ومعاها **زرار "شوف الصفحة"** بيفتح صفحة البائع العامة بالظبط زي ما العميل شايفها، غير زراير التوثيق والإيقاف الموجودة من الأول

## جولة إصلاح شاملة — الأقسام، لوحة التحكم، SEO

بعد ملاحظة إن لوحة التحكم مكنتش فيها كل أزرار التحكم المطلوبة، اتعمل فحص شامل تاني ولقينا الفجوات دي واتصلحت فعليًا (مش بس اتكتبت TODO):

- **مفيش sitemap.xml ولا robots.txt خالص** — جوجل كان أصلاً مش هيقدر يفهرس الموقع. اتضافوا، وبيشملوا كل الأقسام والإعلانات المنشورة بالعربي والإنجليزي
- **روابط "البلاغات" و"الإحصائيات" في اللوحة كانت بتودي لصفحة 404** — اتبنتوا فعليًا: صفحة بلاغات بتدير بلاغات المستخدمين الحقيقية (مع إمكانية إيقاف الإعلان فورًا)، وصفحة إحصائيات بأرقام حقيقية من قاعدة البيانات (مشاهدات، تفاعل، أكتر الأقسام والمناطق نشاطًا، رسم بياني لآخر 14 يوم)
- **زرار "إبلاغ" مكانش موجود خالص** على أي إعلان، مع إن جدول البلاغات كان موجود في قاعدة البيانات من الأول من غير أي طريقة تتملى بيها — اتضاف الزرار + الـ API + صفحة الإدارة، دورة كاملة
- **صفحة إدارة الإعلانات في اللوحة كانت بتجيب بس اللي بانتظار المراجعة** — بقت فيها كل الإعلانات بكل حالاتها، مع بحث وفلتر وإمكانية إيقاف إعلان منشور فعلاً لو فيه مشكلة
- **SEO تقني إضافي**: hreflang/canonical (يربط نسخة الصفحة العربي بالإنجليزي رسميًا لجوجل)، وJSON-LD (Structured Data) على صفحة المنتج عشان جوجل يقدر يعرض السعر والتقييم في نتيجة البحث نفسها
- **البيانات التجريبية اتوسّعت فعليًا**: من محافظتين لـ10 محافظات بمدنهم الحقيقية وإحداثياتهم، ومن قسمين لشجرة أقسام كاملة 3 مستويات (أزياء > رجالي/حريمي/أطفالي، عقارات > بيع/إيجار > شقق/فيلات، إلكترونيات، عربيات، أثاث، 4 خدمات) — بالظبط زي الأمثلة اللي اتقالت

وبعد كل التعديلات دي، اتعاد تشغيل الفحص الكامل من الصفر: **صفر أخطاء TypeScript، صفر مشاكل ESLint، 39/39 اختبار ناجح، بناء إنتاجي كامل ناجح (53+ صفحة)** — مش بس "شكله شغال"، اتأكد فعليًا.

## تحديث التصميم (UI Refresh)

الشكل اتراجع بعد النسخة الأولى عشان يبقى أقرب لمواقع السوق العالمية (زي Amazon/OLX) بدل التصميم الأولي المبني على الـ Figma:

- **شريط أقسام أفقي قابل للتمرير** (Category Strip) تحت الهيدر بدل جدول تصنيفات ثابت — كل قسم ليه أيقونة ولون مميز.
- **لون مميز لكل قسم تلقائيًا**: `src/lib/categoryStyle.ts` بيعمل hash لاسم القسم (slug) ويديله لون ثابت من باليت مدروسة — فأي قسم جديد يضيفه الأدمن بعدين ياخد لون مختلف تلقائيًا من غير ما حد يحدد اللون يدويًا.
- **الصفحة الرئيسية بقت مقسمة بـ "Rails"**: صف أفقي منفصل لكل قسم رئيسي (إلكترونيات، أزياء، أثاث، عقارات، خدمات...) بدل جدول واحد فيه كل المنتجات مخلوطة، وكل صف له لون وأيقونة القسم بتاعه.
- **فلاتر بقت Checkboxes** بدل Dropdown واحد لكل خاصية، مع فاصل سعر (من/إلى)، بشكل أقرب لمواقع التسوق العالمية.
- **لوحة التحكم بقت بـ sidebar غامق بأيقونات** بدل قائمة نصوص بسيطة، وبطاقات المقاييس (Metrics) بقى لها أيقونة ملونة.

جرب المعاينة التفاعلية (نفس التصميم الجديد) من اللينك اللي اتبعت في المحادثة.

## ليه الشكل ده تحديدًا؟ (القرارات الأساسية)

### 1. الأقسام والخصائص Data مش Code
جدول `Category` بيدعم أب/ابن (شجرة) بعمق مفتوح، وكل تصنيف ليه `CategoryAttribute` خاصة بيه
(مثلاً "موبايلات" ليها "المساحة التخزينية" و"الحالة"، بينما "شقق للإيجار" ليها "عدد الغرف" و"المساحة").
لما تضيف قسم جديد أو خاصية جديدة من لوحة التحكم، النموذج (form) بتاع "أضف إعلان" وفلاتر البحث
بيتحدثوا تلقائيًا — من غير أي تعديل في الكود أو نشر (deploy) جديد.

### 2. كل حاجة Dropdown، مفيش كتابة يدوية
أي خاصية بيختارها البائع (المساحة، الحالة، عدد الغرف...) لازم تكون من `AttributeOption` محددة مسبقًا.
ده معمول عشان البيانات تفضل نضيفة وقابلة للفلترة — مفيش "16 جيجا" و"16GB" و"16 GB" في نفس القسم.
المكوّن `DynamicAttributeForm.tsx` هو المسؤول عن رسم الحقول دي.

### 3. SEO من الأساس
كل قسم وكل إعلان ليهم `metaTitle` و`metaDescription` قابلين للتعديل، وNext.js بيعمل server-side
rendering فبمحركات البحث بتقرأ المحتوى مباشرة (عكس مواقع الـ Single Page App اللي بتتعب مع SEO).

### 4. التواصل مجاني وبسيط في البداية
زر "اتصل الآن" و"واتساب" بس — مفيش Chat معقد ولا Payment ولا Escrow دلوقتي، بالظبط زي ما اتفقنا.
لكن الـ schema فيها الأساس (`ProductAttributeValue`, إلخ) بحيث نقدر نضيف الميزات دي تدريجيًا من غير
إعادة بناء قاعدة البيانات من الصفر.

### 5. جاهز للموبايل مستقبلًا
الـ API (`/api/categories`, `/api/locations`, `/api/products`) منفصل عن الـ UI، فتطبيق موبايل React Native
أو Flutter يقدر يستخدم نفس الـ endpoints من غير أي تغيير في الباك إند.

## إزاي تشغّله على جهازك

```bash
npm install
cp .env.example .env          # حط رابط قاعدة بيانات Postgres بتاعتك (Supabase مجاني وسريع للبداية)
npm run db:push               # يبني الجداول في قاعدة البيانات
npm run db:seed                # يحط بيانات تجريبية (أقسام + مواقع)
npm run dev                    # يشغّل الموقع على http://localhost:3000
```

هيوديك تلقائيًا على `/ar` (اللغة الافتراضية)، وتقدر تجرب `/en` أو تستخدم زرار تبديل اللغة في الهيدر.

## الخطوات الجاية (مش موجودة دلوقتي عمدًا)

- 🔲 **صفحة البحث العام** (`/search`) بواجهة كاملة — الـ API (`/api/search`) شغال، ناقص بس صفحة نتائج
- 🔲 **AI Features الأربعة**: Auto Title, Auto Description, Auto Category, Marketing Copy — أماكنهم محجوزة في الفورم (زرار "ساعدني بالذكاء الاصطناعي") وجاهزين لربط API زي Claude
- 🔲 **صفحة إدارة خصائص القسم** من الأدمن (حاليًا بتتضاف عن طريق seed.ts أو مباشرة بقاعدة البيانات)
- 🔲 **صلاحيات الأدمن الفعلية** — لوحة التحكم وروابط الموافقة/الرفض لسه مفتوحة لأي حد عنده الرابط؛ محتاجة تتاكد إن `role === "ADMIN"` قبل ما تنزلها لأي بيئة حقيقية (فيه TODO محدد مكانه في الكود)
- 🔲 **الفلاتر في صفحة القسم لسه شكلية** (checkboxes موجودة بس مش بتعمل query فعلي على القائمة) — محتاجة تتوصل بمنطق فلترة حقيقي

## ميزة "تمييز الإعلان" (Boost) — وطلبات الإعلانات الخارجية

فكرتها: البائع يختار إعلان من إعلاناته، يختار المنصات اللي عايز يميّزه عليها والمدة، يدفع، والإعلان يظهر مميز.

**اللي شغال فعليًا وأوتوماتيك بالكامل:**
- تمييز داخل تريد نفسه (`platforms: ["tureed"]`) — الإعلان بياخد رانك أعلى في الصفحة الرئيسية وصفحات الأقسام (`Product.boostedUntil`)، وBadge "⚡ مميز" يظهر عليه
- صفحة "متابعة إعلاناتي" (`/my-ads`) — **دي بقت خاصة بس بالإعلانات اللي اتعمل لها Boost في يوم من الأيام** (مش كل إعلانات البائع)، وفيها مشاهدات وتفاعل حقيقية (`ViewTracker.tsx` و`ContactButtons.tsx`)، وإمكانية إيقاف التمييز قبل ما ينتهي

**فيسبوك/إنستجرام/تيك توك — طلب يدوي مش نشر أوتوماتيك:**
لما البائع يختار أي من المنصات دي، مبيتحاسبش عليها فورًا. بدل كده بيتعمل `AdRequest` بيظهر في `/admin/ad-requests`، وفريق التسويق بيتواصل مع البائع ويعمله الحملة يدويًا في Meta/TikTok Ads Manager لحد ما يبقى فيه تكامل رسمي. الـ schema (`AdRequest` model) اتصممت من الأول عشان تحمل كل حاجة API التسويق الحقيقي هيحتاجها (منصات، ميزانية يومية، مدة، ملاحظات استهداف) — يعني لما التكامل الرسمي يجهز، التغيير هيكون في خطوة التنفيذ بس (استبدال الموظف بـ API call)، مش في شكل البيانات.

## بروفايل البائع مقابل متابعة الإعلانات — الفرق

- **`/profile`**: كل حاجة تخص حساب البائع — تعديل الاسم/الصورة الشخصية/اسم المتجر/الوصف/واتساب، **وكل إعلاناته أيًا كانت حالتها** (منشور، متوقف، مرفوض...) مع أزرار تعديل/إيقاف/حذف حقيقية
- **`/my-ads`**: بس الإعلانات اللي اتعمل لها Boost — تحليلات المشاهدات والتفاعل والتمييز

## ميزات المشتري: حفظ، سلة، شراء مباشر

على صفحة أي منتج (لغير صاحب الإعلان)، فيه 3 أزرار حقيقية:
- **حفظ (❤️)** — `Favorite` model، موجود من الأول بس دلوقتي متصل بزرار فعلي
- **أضف للسلة (🛒)** — `CartItem` model + صفحة `/cart` لمراجعة السلة
- **اشترِ الآن** — بيظهر بس لو الإعلان له سعر ثابت، وبيعمل `Order`. **ده مرتبط ببوابة الدفع** (تحت)

الثلاثة دول محتاجين تسجيل دخول — الزائر اللي مسجلش بيتحول لصفحة الدخول لو دوس عليهم، لكن التصفح والتواصل (اتصال/واتساب) فاضلين مفتوحين لأي حد.

## بوابة الدفع — موجودة في الكود، متوقفة افتراضيًا

`PlatformSettings` صف واحد بس في قاعدة البيانات فيه `paymentGatewayEnabled` (افتراضيًا `false`)، وأدمن يقدر يبدّله من `/admin/settings`. لما تكون متوقفة:
- طلب "اشترِ الآن" بيتسجل كـ `Order` بحالة `PENDING_PAYMENT` — **مش بيتحسب كعملية بيع حقيقية**، البائع أو فريقكم بيتابعوا يدوي
- طلب تمييز إعلان (`BoostOrder`) بيتسجل بس بيفضل `PENDING_PAYMENT` لحد ما البوابة تتفعل

لما تتفعل من لوحة التحكم، الكود بيحاول يحصّل فعليًا عبر `src/lib/payments.ts` — لسه فيه `MockPaymentProvider` بس (بيرجع نجاح دايمًا) لحد ما تضيف مفاتيح Paymob/Fawry الحقيقية (الكلاسات جاهزة كتعليق في نفس الملف). يعني تفعيل البوابة من غير مفاتيح حقيقية = لسه مش فلوس فعلية، بس ده أقرب خطوة للتفعيل الحقيقي.

## الأقسام والأقسام الفرعية — لأي عمق (مراجعة كاملة)

اتعمل فحص شامل للسؤال ده تحديدًا، ولقينا إن قاعدة البيانات كانت بتدعم شجرة لأي عمق، لكن باقي الكود (الفورم، الفلاتر، صفحة القسم، لوحة التحكم) كان بيفترض مستويين بس. اتبنى من الصفر:

- **`src/lib/tree.ts`** — دوال عامة شغالة لأي عمق (بناء الشجرة، كل الفروع تحت قسم، سلسلة الأجداد، كشف لو النقل هيعمل حلقة لا نهائية) — مختبرة بـ 19 اختبار حقيقي (منهم اختبار صريح لمثال "ملابس > رجالي > أحذية > أحذية رياضية" بـ4 مستويات)
- **`CascadingTreeSelect`** — عنصر واحد بيتكرر لأي عدد مستويات: يظهر Dropdown الأب، ولما تختار منه يظهر اللي بعده **بس لو عنده أبناء**، وهكذا لحد آخر مستوى. نفس العنصر بالظبط مستخدم في فورم رفع الإعلان (لازم توصل لآخر مستوى) **وفي صفحة البحث** (تقدر توقف عند أي مستوى — زي ما طلبت بالظبط: "نفس الفكرة في البحث")
- **الحقول بتورث من الأجداد**: لو حطيت خاصية "الموسم" على قسم "ملابس"، هي تلقائيًا هتظهر لأي بائع بيرفع في "رجالي" أو "رجالي > أحذية" من غير ما تكررها — `getEffectiveAttributes()` بتجمعها من الجد لحد القسم نفسه
- **لوحة التحكم**: `/admin/categories` بقت شجرة تفاعلية — تقدر تضيف "قسم فرعي" جوه أي قسم موجود أيًا كان عمقه، وتدوس "الحقول" على أي قسم تدير خصائصه (إضافة حقل Dropdown جديد وقيمه بالجملة، سطر لكل خيار)
- **قاعدة صارمة**: البائع ميقدرش ينشر إعلان إلا في **آخر مستوى فعلي** (قسم مالوش أبناء) — لو حاول ينشر في "عقارات" نفسها من غير ما يحدد "بيع" ثم "شقق"، السيرفر بيرفضه (`checkPostableCategory`)، مش بس الواجهة

- **باق (Bug) حقيقي في تعديل/حذف الإعلان:** الكود كان بيدور عن المنتج بالـ `id` الداخلي بتاع قاعدة البيانات، لكن الواجهة كانت بتبعت الـ `slug` — يعني زرار "تعديل" و"حذف" و"إيقاف" في صفحة البروفايل كانوا **مش هيشتغلوا خالص** (هيرجعوا "مش موجود" دايمًا). اتصلح.
- **رفع الصور كان بيثق في نوع الملف اللي بيبعته المتصفح** (`file.type`) **وامتداد اسم الملف** — وده سهل التلاعب بيه: حد يقدر يرفع ملف HTML فيه كود خبيث ويسميه `image.jpg` ويقول للسيرفر "أنا صورة". دلوقتي السيرفر بيتحقق من أول بايتات الملف نفسه (Signature حقيقي لـ JPEG/PNG/WEBP) مش من اللي المستخدم بيدّعيه.
- **مفتاح تشفير الجلسة (`AUTH_SECRET`) كان ليه قيمة احتياطية افتراضية** — لو حد نسي يحددها في production، أي حد يعرف الكود (ده كود مفتوح المصدر ليك) يقدر يزوّر جلسة دخول باسم أي مستخدم، **حتى أدمن**. دلوقتي السيرفر بيرفض يشتغل في production لو المتغير ده مش متظبط بقيمة حقيقية.

### 🟠 مشاكل متوسطة (تعطل أو استغلال محدود)

- مفيش أي حد كان بيتحقق من إن الحساب **موقوف (Suspended)** قبل ما يسمحله ينشر إعلان/يميّزه/يشتري — يعني أدمن يوقف حساب، والشخص يفضل يقدر يعمل كل حاجة لحد ما الجلسة (30 يوم) تنتهي. ضفنا `getActiveUser()` بيتحقق من الحالة كل مرة في نقاط النشر/الشراء/التمييز.
- مراجعات البائعين (Reviews) كان ممكن نفس المشتري يبعت عشرات المراجعات على نفس البائع ويأثر على متوسط التقييم بشكل غير عادل — ضفنا قيد (Unique Constraint) يخلي كل مشتري له مراجعة واحدة بس لكل بائع (لو كررها بتتحدّث مش بتتضاف).
- نقاط API كتير (تقريبًا 15) كانت بتثق في البيانات الجاية من المتصفح من غير أي تحقق — سعر سالب، نص فاضي، أرقام غير منطقية، JSON تالف كان بيعمل كراش (خطأ 500) بدل رسالة واضحة. راجعناها كلها وضفنا تحقق حقيقي (validation) بدل ما نسيبها تثق في أي حاجة.
- رفع الصور وتتبع المشاهدات/التفاعل (`/api/upload`, `/api/products/[id]/track`) مكنش عليهم أي حد أقصى (Rate Limit) — سكريبت بسيط كان يقدر يضخّم أرقام المشاهدات وهمي أو يملى مساحة التخزين. ضفنا حدود معقولة.

### 🟡 حاجات معروفة ولسه محتاجة شغل (موثّقة صراحة مش مخبّية)

## النشر المجاني (MVP) + GitHub

1. **GitHub:** `git init` ← `git add .` ← `git commit -m "baseline"` ← اعمل repo خاص (Private) على github.com ← `git remote add origin ...` ← `git push -u origin main`. كل تعديل بعد كده = commit جديد، ومفيش zip تاني.
2. **قاعدة البيانات:** Supabase (مجاني) ← `DATABASE_URL` من الـ Transaction pooler (بورت 6543 + `?pgbouncer=true&connection_limit=5`). شغّل `npm run db:push` مرة من جهازك على نفس الـ URL (والـ seed لو عاوز داتا تجريبية).
3. **الصور:** Cloudflare R2 (مجاني 10GB) ← فعّل Public access على الـ bucket وحط متغيرات `S3_*` (الكود بيستخدمها تلقائيًا لما تكمل كلها). من غيرها رفع الصور مش هيشتغل على الاستضافة.
4. **الاستضافة:** Vercel ← Import من GitHub ← حط Environment Variables (`DATABASE_URL`, `AUTH_SECRET`, `NEXT_PUBLIC_SITE_URL`, `ADMIN_DB_PASSWORD`, `S3_*`, واتساب) ← Deploy. أي push على `main` بينشر تلقائيًا.
5. **ملاحظة:** خطة Vercel Hobby للاستخدام غير التجاري. أول ما تبدأ إعلانات/اشتراكات انقل لخطة Pro أو استضافة تانية.
